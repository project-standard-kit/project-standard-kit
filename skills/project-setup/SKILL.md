# 프로젝트 셋업

이 스킬 하나로 표준 틀 5절 0~4단계(개발 전)를 끝내 "바로 개발할 수 있는 상태"를 만든다. 리더는 질문에 고르기만 하고, 문서·인프라 설계·저장소 설정은 이 스킬이 만든다.

## 위치 정하기

| 무엇 | 찾는 순서 |
|---|---|
| 표준 틀(이하 `<틀>`) | ① `$PROJECT_STANDARD_DIR` ② `$OBSIDIAN_VAULT_PATH/30 Areas/Development Standard/` ③ 이 스킬 폴더의 `standard/`(함께 배포된 사본) |
| 프로젝트 문서 | `$OBSIDIAN_VAULT_PATH`가 있으면 `$OBSIDIAN_VAULT_PATH/20 Projects/<프로젝트>/`. 없으면 첫 질문 묶음에서 "문서를 어디에 둘까"를 묻는다(권장: 옵시디안 볼트 경로, 대안: 서버 저장소 `docs/project/`) |
| 코드 저장소 | `$WORKSPACE/<프로젝트>/`, 없으면 지금 작업 폴더 아래 `<프로젝트>/`를 권장안으로 묻는다 |
| 비밀정보 | `$SECRETS_ROOT/<프로젝트>/<환경>/`, 없으면 `~/.secrets/<프로젝트>/<환경>/`을 권장안으로 B8에서 묻는다 |

- 문서 안의 `$OBSIDIAN_VAULT_PATH`·`$WORKSPACE`·`$SECRETS_ROOT`·`$BACKUP_ROOT`는 위에서 정한 실제 경로로 읽는다.
- 사용자 전역 지침(`CLAUDE.md`·`AGENTS.md`)에 저장 위치·언어 런타임 규칙이 있으면 이 표보다 그것을 따른다.
- 표준 틀 링크(`[[30 Areas/Development Standard/...]]`)는 틀이 볼트의 그 경로에 있을 때 열린다. ③ 사본을 쓰면 보고에 "볼트에 틀을 설치하면 링크가 열린다"를 적는다.

## 0. 읽기

1. 프로젝트 문서 위치의 `AGENTS.md`(있으면).
2. `<틀>/양식/프로젝트 개발 규약 양식.md` — **질문지와 결과 틀의 정본.** 질문은 여기서 읽는다(이 스킬에 복사하지 않는다. 양식이 바뀌면 질문도 바뀐다).
3. `<틀>/프로젝트 표준 틀.md` 2절(위치), 4절(문서 형식), 5절(체크리스트), 6절(팀 기본값). `<틀>/개발 규약/` 각 문서의 "공통 규칙"과 "예". `<틀>/양식/`의 시스템 설계·도메인 문서·결정 기록 양식.
4. 프로젝트 폴더가 이미 있으면 기획서, 시스템 설계, 도메인 목록을 읽는다. 있는 것은 덮어쓰지 않고 빈 칸만 채운다. 이미 정해진 질문은 묻지 않는다.

## 1. 권장안 정하기

질문마다 권장안 하나를 고른다.
- 기획(목표, 사용자, 규모, 예산, 외부 연동)을 근거로 한다. 근거를 옵션 설명에 한 줄로 쓴다("하루 사용자 1천 명 미만이라 집에 있는 상시 장비로 충분").
- 근거가 없으면 팀 기본값(표준 틀 6절, 각 규약 문서의 "예").
- 앞 답이 뒤 권장안을 바꾼다. 예: 환경 "개발만" → 배포·백업·알림 질문은 "첫 배포 전에 다시" 권장 / 외부 노출 "공개 웹" → 상시 켜진 서버, Tunnel, 퍼블릭 API 포함.

## 2. 묻기

- 양식 질문지의 묶음 순서대로, `AskUserQuestion` 한 번에 질문 최대 4개.
- 권장안을 첫 옵션으로, 라벨 끝에 `(권장)`. 옵션 2~4개, 나머지는 "Other". 여럿 고르는 질문은 `multiSelect: true`.
- 질문 문장만 봐도 이해되게 쓴다(앞 결과가 화면에 안 보일 수 있다).
- 이름·한 줄 목표처럼 고를 수 없는 것은 기획서에서 뽑은 후보를 옵션으로 내고, 없으면 "Other"로 받는다.
- 도메인은 기획에서 나눈 안(도메인 이름, 책임, API 경로 자원, 오류 코드 접두어)을 표로 보여 주고 "이대로 / 고쳐서"로 묻는다.
- 리더가 "알아서"·"권장대로"라고 하면 남은 질문은 권장안으로 정하고 `제안`으로 표시한다.
- 답끼리 충돌하면(예: 예산 0원 + 유료 관리형 DB) 한 번만 짧게 되묻는다.
- 마지막에 정한 것 전체를 표로 보여 주고 "이대로 만들기 / 고칠 것 있음"을 묻는다. 확인 뒤에만 3단계로 간다.

## 3. 만들기

양식의 "만들어지는 것" 표를 모두 만든다. 그림과 문서는 따로 요청받지 않아도 만든다.

**프로젝트 문서** (위치는 표준 틀 2.2절)
- 프로젝트 입구 문서(2.6절), `기획/` 요약(없을 때), frontmatter에 틀 버전.
- `개발/시스템 설계/시스템 설계.md`: 1~3절(맥락, 목표·비목표, 제약), 4.1 **시스템 컨텍스트 그림**(Mermaid), 4.2 모듈 구성, 4.5에 인프라 문서 링크, 8절 위험·미결.
- `개발/시스템 설계/기술·인프라/인프라.md`:
  - **인프라 구성도**(Mermaid `flowchart`): 사용자·외부 서비스 → 진입(Tunnel·프록시) → 서비스 프로세스 → DB, 백업 대상, 알림 경로. 환경이 여럿이면 `prod` 기준으로 그리고 다른 환경의 차이는 표로.
  - 환경 표(이름, 위치, 주소, 데이터, 누가 배포). "개발만"이면 운영 칸은 "첫 배포 전에 정함".
  - 시스템 설계 양식 4.5절 여섯 질문(어디서 도나, 어떻게 뜨나, 누가 어떻게 들어가나, 데이터는 안전한가, 고장 나면 어떻게 아나, 얼마 드나)에 모두 답한다. 모르는 값은 "미정 — 이유, 언제 정하나".
- `개발/도메인/도메인 목록.md`와 도메인마다 빈 도메인 문서(`<틀>/양식/도메인 문서 양식.md`).
- `개발/<프로젝트> 개발 규약.md`: 양식의 "결과 문서 틀"을 답으로 채운다.
- `개발/결정 기록/`: 되돌리기 어려운 선택(환경 구성, 서버 위치, DB, 외부 노출, 배포 방식, 모듈 구성)마다 하나. 리더가 고른 것은 `승인`, 넘긴 것은 `제안`.

**클라이언트와 서버** — 대부분 짝이다. 클라이언트가 있으면 클라이언트 저장소도 아래 저장소 항목을 그 언어로 똑같이 만든다(레이어 폴더, 린트·포맷, 아키텍처 테스트, `check.sh`, CI, PR 템플릿). 더해서:
- 서버 OpenAPI에서 클라이언트 API 코드를 만드는 명령, 오류 코드별 공통 처리 한 곳, 환경별 API 주소 설정.
- 서버 `GET /health`와 최소 지원 앱 버전 응답(앱일 때).
- 시스템 컨텍스트 그림과 인프라 구성도에 클라이언트(앱 스토어·웹 호스팅 포함)를 그린다.

**모듈 저장소** (모듈마다, 위치는 위 "위치 정하기")
- `git init`, `main`·`develop`. 원격 생성·push는 리더에게 확인한 뒤에만.
- 표준 틀 2.4절 폴더, `AGENTS.md`(틀 버전·문서 경로·주요 명령·사람 확인 지점), `README.md`, `.env.example`(이름만), `docs/interfaces/`, `docs/specs/<도메인>.md`.
- 검사: 린트·포맷·타입 설정, 아키텍처 테스트 설정(레이어 + `domain` 금지 패키지), 커밋 훅, `scripts/check.sh`(CI 6절 일곱 검사), CI 워크플로, `.github/pull_request_template.md`(코드 리뷰 15절 네 칸).
- 첫 코드: 진입점, 설정 검증, 구조화 로그, 기반 오류와 오류 응답 형식, `GET /health` — 개발 규약 2·3절 공통 컨벤션대로.
- 환경에 따라 `deploy/`: 배포 스크립트(태그를 받음), 서비스 정의(launchd·systemd·Compose), 백업 스크립트. "개발만"이면 만들지 않고 할 일로 남긴다.
- Python이면 `uv`로 `.venv`를 만든다(사용자 전역 런타임 규칙이 있으면 그것을 따른다).
- 만든 뒤 `scripts/check.sh`를 실제로 돌려 통과시킨다. 아키텍처 테스트는 금지 import를 잠깐 넣어 실패하는지 확인하고 되돌린다. 도구가 설치돼 있지 않아 못 돌린 검사는 "못 돌림 — 설치 명령"으로 보고한다.

**하지 않는 것** — 할 일 목록으로 남기고 리더가 한다
- 비밀정보 값 입력, 계정 로그인·가입, 유료 자원 생성, 서버 접속·설치, 이슈 트래커 프로젝트 생성, 원격 저장소 공개 설정, 운영 배포.

## 4. 보고 (사용자 언어, 기본 한국어)

- 정한 것 표(질문, 답, 승인/제안).
- 쓴 표준 틀 위치(①②③ 중 무엇)와 만든 파일 목록(문서, 저장소).
- 실행한 검사와 실제 결과.
- 리더가 직접 할 일(키 발급·입력, 원격 저장소, 서버 준비, 이슈 트래커, 첫 배포)과 그 다음 단계(표준 틀 5절 5~6).
