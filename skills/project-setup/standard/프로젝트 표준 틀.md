# 프로젝트 표준 틀 (v0.16)

> 표기: [FACT] 출처에서 직접 확인, [CLAIM] 출처 작성자·회사의 주장, [INFERENCE] 이 문서의 종합·판단. 기준일 2026-10-25.

## 0. 이 문서가 하는 일

- **목적.** 어떤 프로젝트를 하든, 개발자가 한 명이든 팀이든 같은 틀 위에서 개발한다. 무엇이 새로 생겨도 "어느 영역의, 어느 단계의, 어느 위치"에 둘지 이 문서로 정한다.
- **적용 범위.** 새로 시작하는 모든 개발 프로젝트.
- **원칙.**
  1. **자리는 미리 정하고, 내용은 필요할 때 채운다.** 위치 지도는 처음부터 완성하고, 쓰지 않을 문서는 만들지 않는다.
  2. **문서는 그 문서가 설명하는 대상과 같은 곳에 둔다**(2절).
  3. **틀은 프로젝트 밖 한 곳에만 둔다.** 프로젝트는 틀을 복사하지 않고 가리킨다.
  4. **작업 크기에 맞춰 문서 양을 정한다**(3절).
  5. **상상으로 키우지 않는다.** 실제 프로젝트에 쓰면서 고친다.
  6. **틀도 제품처럼 다룬다.** 버전을 붙이고, 프로젝트마다 어느 버전의 틀을 따르는지 적는다.

## 1. 전체 틀: 영역 × 단계

### 1.1 영역 8개 (무엇을 설계·관리하나)

[FACT] 엔터프라이즈 아키텍처 표준 TOGAF는 업무·데이터·애플리케이션·기술 4개 영역(BDAT)으로 나누고([Visual Paradigm](https://togaf.visual-paradigm.com/2025/02/18/comprehensive-guide-to-architecture-domains-in-togaf/)), 국내 정보기술아키텍처는 여기에 보안을 더한다([서울시](https://news.seoul.go.kr/gov/?p=1265), [IT위키](https://itwiki.kr/w/EA)). [INFERENCE] 이 틀은 여기에 제품 디자인, 운영, AI 협업을 더한다.

| 영역 | 다루는 것 | 대표 결과물 |
|---|---|---|
| 업무 | 무엇을 왜 하나. 요구사항, 업무 규칙, 성공 기준 | 기획서, 수용 기준 |
| 제품 디자인 | 사용자가 보고 겪는 것. 사용자 흐름(UX), 화면(UI), 메시지·카피, 브랜드, 디자인 시스템 | 제품 디자인 문서, Figma 원본 |
| 데이터 | 무엇을 저장하고 얼마나 보관하나. 데이터 출처와 품질 | 데이터 모델, 보관·삭제 규칙, 품질 검사 |
| 애플리케이션 | 어떤 구성 요소가 어떻게 연결되나. 모듈 구성, 코드 구조, 외부 연동 | 시스템 설계, 모듈 간 약속, 코드 |
| 기술·인프라 | 어디서 어떻게 돌아가나. 실행 환경, 배포, 자동 시작, 백업 | 배포 구조, 환경 설정 |
| 보안·규정 | 키·계정·권한, 공급망(외부 패키지), 개인정보, 법·약관 | 비밀정보 규칙, 규정 점검표 |
| 운영 | 모니터링, 목표 수준(SLO), 장애 대응, 비용, 사후 분석 | 운영 절차, 지표, 비용 표 |
| AI 협업 | AI 사용 원칙, AI가 읽을 지도, 스펙 중심 작업 흐름 | `CLAUDE.md`, 스펙 |

**개발 설계와 제품 디자인의 구분.** 제품 디자인은 "사용자가 무엇을 보고 겪는가", 개발 설계(애플리케이션·데이터·기술 영역)는 "그것을 어떻게 만들고 돌리는가"를 다룬다.

### 1.2 단계 7개 (언제 하나)

기획 → 설계 → 개발 → 검증 → 배포 → 운영 → 개선·정리 → (다시 기획)

| 단계 | 목표 | 끝났다는 기준 | 승인 |
|---|---|---|---|
| 기획 | 무엇을 왜, 어디까지 | 범위·비목표·성공 기준 확정 | 프로젝트 책임자 |
| 설계 | 무엇을 보여 주고, 어떻게 만들고 돌릴지 | 제품 디자인·시스템 설계 승인, 큰 결정은 ADR | 프로젝트 책임자(제품), 개발 리더(시스템) |
| 개발 | 기능(에픽) 단위로 만들기 | 기능의 티켓 병합, 테스트 통과, 현행 명세 갱신 | AI 1차 리뷰 + 사람 승인 |
| 검증 | 스펙대로 동작하나, 쓰는 사람이 쓸 수 있나 | 수용 기준 통과, 보안·규정 점검 통과 | 스펙에 적힌 확인자 |
| 배포 | 운영 환경에 안전하게 반영 | 반영 완료, 되돌리기 방법 확인 | 개발 리더 |
| 운영 | 목표 수준 유지 | SLO 안에서 동작, 장애 대응 기록 | 운영 담당 |
| 개선·정리 | 배운 것 반영, 안 쓰는 것 치우기 | 회고·사후 분석 반영, 정리 절차 완료 | 프로젝트 책임자 |

### 1.4 영역과 단계에 모두 걸치는 것

- **측정.**
  - [FACT] DORA 4대 지표: 배포 빈도, 변경이 반영되기까지 걸린 시간, 변경 실패율, 복구 시간([DORA](https://dora.dev/dora-report-2025/)).
  - 제품 지표: 사용자 수, 이탈, 핵심 행동. 1인 개발이면 수동 기록으로 시작한다.
- **결정 기록(ADR).** 비싸거나, 되돌리기 어렵거나, 논쟁이 있는 결정 하나당 짧은 기록 하나를 쓴다(번호, 제목, 맥락, 결정, 결과, 상태). 결정을 뒤집을 때는 기존 기록을 고치지 않고 새 기록을 쓴다. 예외는 이전 기록의 상태를 `대체됨`으로 바꾸는 것뿐이다([Red Hat](https://redhat.com/en/blog/architecture-decision-records)). 위치는 결정의 범위에 따라 다르다(2.3절).

## 2. 위치

### 2.1 위치 원칙: 세 단계

**문서는 그 문서가 설명하는 대상과 같은 곳에 둔다.**

| 단계 | 설명 대상 | 위치 |
|---|---|---|
| 틀 | 모든 프로젝트 | 옵시디안 `30 Areas/Development Standard/`. 코드 시작 템플릿만 `<유형>-conventions` 저장소 |
| 프로젝트 | 프로젝트 전체: 사업, 사용자 경험, 여러 저장소에 걸친 것 | 옵시디안 `20 Projects/<프로젝트>/` |
| 모듈 | 한 저장소의 코드 | 그 모듈 저장소 |

- [INFERENCE] 사람이 읽고 생각하는 문서는 옵시디안에 둔다. 코드와 같이 바뀌어야 하고 리뷰·자동 검사·AI가 함께 봐야 하는 문서는 저장소에 둔다.
- 저장소가 여러 개여도 프로젝트 문서는 옵시디안 프로젝트 폴더 한곳에 모인다. 그래서 별도 문서 저장소를 만들지 않는다.
- 옵시디안 프로젝트 폴더의 `개발/`은 나중에 개발팀이 생기면 팀 공유 공간으로 통째로 옮길 단위다.

### 2.2 전체 위치 지도

```text
$OBSIDIAN_VAULT_PATH/                       ← 옵시디안: 사람이 읽는 문서
├── 30 Areas/Development Standard/              ← 틀(모든 프로젝트 공통)
│   ├── 프로젝트 표준 틀.md                  ← 정본(이 문서)
│   └── 양식/                                    ← 시스템 설계·ADR·스펙·운영 절차·제품 디자인 양식(처음 쓸 때 만듦)
└── 20 Projects/<프로젝트>/                      ← 프로젝트 전체에 걸친 문서
    ├── <프로젝트>.md                             ← 입구: 폴더 규칙표, 현행 기준 문서 목록, 구조 변경 담당(2.6절)
    ├── <프로젝트> 사업 기획서.md
    ├── 기획/                                     ← 정책(화면 사이 규칙), 화면 설계·IA(4.5절). 문서마다 변경 이력 표
    ├── 제품 디자인/                              ← 사용자 흐름, 화면, 카피, 브랜드(+ Figma 링크)
    ├── 기능/                                     ← 진행 중인 일. 입구 `기능 목록.md`(4.3절)
    │   └── <에픽 키> <기능>/                    ← 에픽 하나: `<기능>.md`(양식/기능 문서 양식) + 기획/·디자인/ 초안 + 개발 하위 작업 폴더(개발 규약 13절)
    ├── 개발/                                     ← 팀이 생기면 통째로 옮길 단위
    │   ├── 시스템 설계/                          ← 입구 문서 + 영역 폴더(4.1절)
    │   │   ├── 시스템 설계.md                    ← 입구: 양식 1~9절 순서, 상세는 링크
    │   │   ├── 애플리케이션/                     ← 모듈 구성(저장소 링크), 테스트 전략, 흐름/, 외부 연동/. 저장소 전 설계 초안만 <모듈>/
    │   │   ├── 데이터/                           ← 저장·보관
    │   │   ├── 기술·인프라/                      ← 배포 구조, 실행 환경, 환경 표
    │   │   ├── 보안·규정/                        ← 약관, 개인정보, 권한
    │   │   └── 운영/                             ← 오류 처리, 로깅, SLO 설계
    │   ├── 도메인/                               ← 도메인별 정리본(셋업 때 나눔). 입구 `도메인 목록.md`(4.3절)
    │   │   └── <도메인>/<도메인>.md              ← 지금 규칙·동작 요약 + 변경 이력. 기능 완료 때 갱신(양식/도메인 문서 양식)
    │   ├── 결정/                                 ← 여러 저장소·운영 전반에 걸친 결정
    │   └── 운영/                                 ← 반복 운영 업무: 절차(서버, 키 교체, 백업, 장애 대응, 모니터링 도구 목록) + 배포/
    │       └── 배포/                             ← 배포 1회 = 문서 1개(양식/배포 기록 양식) + 대기 목록
    ├── 회의/                                     ← 날짜별. 결정은 개발/결정/로 옮겨 링크
    ├── 회고/                                     ← 회고, 사후 분석
    └── 보관/                                     ← 끝난 1회성 산출물(구축 기록, PoC, 지난 세대 문서)

$WORKSPACE/
├── <유형>-conventions/                          ← 모듈 유형별 코드 시작 템플릿(골든 패스)
└── <프로젝트>/                                  ← 프로젝트 폴더(Git 아님): 모듈 저장소 묶음
    ├── <프로젝트>-<모듈>/                        ← 모듈 저장소(Git): 코드와 같이 바뀌는 것만(2.4절)
    └── runtime/                                 ← 운영 DB·로그(Git 아님)

$SECRETS_ROOT/<프로젝트>/                   ← 운영 키(명의자만 접근, AI 읽기 금지)
$BACKUP_ROOT/<프로젝트>/     ← 백업(장기 보존)
~/worktree/<프로젝트>/<작업명>/                   ← 작업용 워크트리(필요할 때만)
~/worktree/.tmp/<작업명>/                         ← 임시 파일
```

- 운영 데이터·비밀정보·백업·워크트리·임시 파일 위치는 사용자 저장 규칙(`~/.agents/project-storage-rules.md`의 Storage 절)을 따른다.
- 비밀정보를 프로젝트 폴더 밖에 따로 두는 이유: AI 에이전트가 모듈 저장소에서 일하다가 상위 폴더까지 읽을 수 있기 때문이다.
- `runtime/`과 `secrets/` 경로는 v0.2 제안이며, 첫 적용 프로젝트에서 결정 기록으로 확정한다.

### 2.3 헷갈리기 쉬운 것의 위치

| 문서 | 한 모듈 안에서 끝나면 | 여러 모듈·운영 전반에 걸치면 |
|---|---|---|
| 결정(ADR) | 모듈 저장소 `docs/adr/`가 정본 | 여러 저장소에 걸친 결정만 옵시디안 `개발/결정/`. 기능·티켓 폴더에는 링크만 둔다 |
| 현행 명세(지금 어떻게 동작하나) | 모듈 저장소 `docs/specs/<도메인>.md` | 모듈마다 자기 몫을 저장소에 쓰고, 흐름은 `시스템 설계/애플리케이션/흐름/` |
| 도메인 문서(사람이 읽는 정리본) | 옵시디안 `개발/도메인/<도메인>/<도메인>.md`. 기능 완료 때 저장소 현행 명세에서 가져와 정리 | 같음 |
| 기능 문서(이번에 무엇을 왜 바꾸나) | 옵시디안 `기능/<에픽 키> <기능>/<기능>.md` | 같음. 영향받는 모듈·도메인을 모두 적는다 |
| 운영 절차 | 모듈 저장소 `docs/runbook/` | 옵시디안 `개발/운영/` |
| 모듈 간 약속(데이터 형식·API) | 제공하는 쪽 모듈 저장소 `docs/interfaces/`가 정본. 쓰는 쪽은 링크만 | |
| 제품 디자인 | 디자인 문서는 옵시디안 `제품 디자인/`, 시각 원본은 Figma, 구현 코드(메시지·화면 템플릿, 디자인 토큰)는 모듈 저장소 `src/` | |
| 기획 vs 제품 디자인 | 정책(권한·알림 조건·다국어 등 화면 사이 규칙)과 화면별 동작·필드 정의는 `기획/`. 사용자 흐름·카피·브랜드·시각은 `제품 디자인/` | |
| 외부 연동 | 받는 쪽 연동(외부 API를 부름)은 `시스템 설계/애플리케이션/외부 연동/<시스템>.md` | 주는 쪽(외부가 이 시스템을 부름)은 제공 모듈 저장소 `docs/interfaces/`가 정본 |
| 배포 기록 | 모듈 하나만 배포해도 프로젝트 `개발/운영/배포/` | |

### 2.4 모듈 저장소 구조

Python 기준이고, 헥사고날 구조(포트와 어댑터)를 폴더로 옮긴 형태다. [CLAIM] 헥사고날 구조는 업무 로직을 가운데 두고 기술을 바깥 어댑터로 두며, 의존은 바깥에서 안쪽으로만 흐른다([arc42 Quality](https://quality.arc42.org/approaches/hexagonal-architecture)). 저장소에는 일반 규칙을 복사하지 않는다. 이 절이 정본이다.

```text
<프로젝트>-<모듈>/
├── README.md            # 무엇을 하는지, 실행 방법, 이 모듈만의 특이사항
├── CLAUDE.md            # 따르는 틀 버전과 경로, 프로젝트 문서 경로, 이 모듈 고유 규칙
├── pyproject.toml
├── .env.example         # 필요한 비밀정보 이름만(값 없음)
├── config/              # 환경별 설정(비밀 제외)
├── docs/                # 이 모듈 코드와 같이 바뀌는 문서만
│   ├── adr/             # 이 모듈 코드에 대한 결정 0001-*.md
│   ├── specs/           # 현행 명세 <도메인>.md: 지금 동작·수용 기준. 동작을 바꾸는 PR이 같이 고친다(4.3절)
│   ├── interfaces/      # 이 모듈이 제공하는 약속
│   └── runbook/         # 이 모듈 운영 절차
├── src/<패키지>/
│   ├── domain/          # 업무 규칙. 외부를 전혀 모름 (레이어 폴더마다 README.md: 역할과 규칙)
│   ├── app/             # 기능 흐름과, 바깥에 기대하는 기능의 약속(포트)
│   ├── adapters/
│   │   ├── inbound/     # 들어오는 것: 예약 작업, 봇 명령, CLI
│   │   └── outbound/    # 나가는 것: 외부 API, DB, 메신저, 정적 사이트
│   ├── platform/        # 공통 기반: 설정·비밀, 로그 출력 설정, 시각 공급, 외부 호출(재시도·속도 제한·robots) 구현
│   └── main.py          # 조립: 어느 어댑터를 어느 포트에 끼울지
├── tests/               # src와 같은 구조 + fixtures/
├── scripts/             # 일회성·운영 보조 스크립트
├── deploy/              # 이 모듈의 자동 시작 설정, 환경 준비
└── var/                 # 개발계 실행 데이터. Git 제외
```

**코드 안에서 새로 생긴 것은 어디에 두나**

| 생긴 것 | 위치 |
|---|---|
| 새 외부 API 연동 | `adapters/outbound/<서비스>/` |
| 새 입력 경로(봇 명령, 예약 작업) | `adapters/inbound/` |
| 새 업무 규칙 | `domain/` |
| 새 기능 흐름 | `app/` + `docs/specs/<도메인>.md` 갱신 |
| 다른 프로젝트도 쓸 기능 | `platform/` → 다음 버전의 `<유형>-conventions`에 반영 |
| 설정값 / 비밀정보 | `config/` / 저장소 밖(`.env.example`에는 이름만) |
| 테스트 | `tests/` 아래 같은 경로 |

**의존 방향 규칙**

- `domain`은 프로젝트의 다른 폴더를 쓰지 않는다. 표준 라이브러리(`logging` 포함)는 쓸 수 있고, 프레임워크·DB·HTTP 라이브러리는 모른다.
- `app`은 `domain`과 표준 라이브러리만 쓴다. 시각·외부 연결처럼 바깥에 기대는 것은 포트(약속)로 정의하고, 구현은 `platform`·`adapters`가 맡는다.
- `adapters`는 `app`·`domain`·`platform`을 쓴다.
- `platform`은 `adapters`와 `main.py`가 쓴다. `app`·`domain`이 `platform`을 직접 import하는 것은 금지다.
- 시각, 로그 출력 설정, 외부 연결은 `platform`/`main.py`가 만들어 `app`·`domain`에 주입한다(시각은 호출자가 `now` 인자로 넘긴다).
- 전부를 아는 곳은 `main.py` 하나다.

이 규칙은 사람 리뷰가 아니라 아키텍처 테스트로 자동 검사한다(CI 검사 진입점에 포함). 도구는 모듈 언어마다 셋업 때 정한다([[30 Areas/Development Standard/개발 규약/아키텍처 레이어|개발 규약]] 1절). 클라이언트 모듈도 같은 방향(화면 → 상태·유스케이스 → 도메인 ← 데이터 어댑터)을 따른다.

### 2.6 구조 유지 규칙

근거: 오래 운영한 문서 공간을 보면 1회성 구축 산출물 폴더는 구축이 끝나며 멈추고, 반복 업무 폴더(배포·운영·오픈)만 계속 쓰인다. 번호 다시 매기기, 늦은 이동 안내, 담당이 바뀐 뒤 구조가 굳는 일이 흔하다.

1. **입구 문서.** 프로젝트 폴더의 `<프로젝트>.md`에 폴더 규칙표(폴더·담는 것·현행 기준 문서)와 구조 변경 담당을 적는다. 새 폴더를 만들면 규칙표에 한 줄을 더한다. 담당이 바뀌면 인수인계 문서 대신 현행 기준 문서 목록을 갱신한다.
2. **한 층에 분류 기준 하나.** 프로젝트 최상위는 산출물 종류, `시스템 설계/` 아래는 영역(1.1절). 기술 영역 폴더를 최상위로 올리지 않는다.
3. **번호 접두어를 쓰지 않는다.** 정렬은 이름으로 한다. 번호를 바꾸면 링크와 기억이 어긋난다.
4. **구축용과 운영용을 나눈다.** 반복 업무(배포, 릴리스, 오픈, 장애 대응)는 첫 회에 틀 `양식/`에 공통 양식을 만들고, 기록은 `개발/운영/`에 둔다. 프로젝트마다 양식 사본을 두지 않는다(원본과 어긋남). 모듈 목록·배포 순서처럼 프로젝트마다 다른 내용은 입구 문서나 `개발/운영/` 런북에 적는다. 한 번 하고 끝나는 기록(환경 구축, 도구 PoC, 지난 세대 설계)은 끝나면 `보관/`으로 옮긴다.
5. **옮기면 그날 안내를 남긴다.** 원래 자리에 "→ 새 위치" 한 줄. 옵시디안 안에서는 위키 링크가 자동으로 따라오므로 볼트 밖에서 링크한 곳만 챙긴다.
6. **분기 점검.** 분기마다 3개월 넘게 안 바뀐 폴더를 본다. 운영 폴더면 갱신하고, 1회성 산출물이면 `보관/`으로 옮긴다.
7. **회의록의 결정은 ADR로 옮긴다.** 회의록은 날짜별로 두고, 결정은 `개발/결정/`에 ADR로 쓰고 회의록에서 링크한다.
8. **문서 본문에 비밀번호·키를 쓰지 않는다.** 위치(`$SECRETS_ROOT/<프로젝트>/`의 파일 이름)만 적는다.
9. **자리만 두는 것.** 다고객·다법인 프로젝트는 `<고객>/` 폴더(개요·요건·이관·오픈)를, 계약 산출물 제출이 있으면 "제출 목록 문서 하나 + Git 태그·PDF"를 그때 추가한다. 원본을 복사한 제출본 폴더는 만들지 않는다.

## 3. 작업 크기별 문서 양

| 작업 크기 | 남기는 것 |
|---|---|
| 작은 수정(버그, 문구, 설정) | 이슈 또는 커밋 메시지 |
| 기능 하나 | 기능 문서(무엇·왜·스토리·영향 도메인, 1~2쪽) + PR마다 현행 명세 갱신 + 끝날 때 도메인 문서·`기획/`·`제품 디자인/` 반영. 4.3절 |
| 새 시스템, 구조 변경 | 시스템 설계(옵시디안 `개발/시스템 설계/`) + 결정 기록 |
| 사용자에게 보이는 변화 | 기능 폴더 `기획/`·`디자인/`에 초안, 기능 완료 때 `기획/<도메인>/`·`제품 디자인/<도메인>/`에 반영하고 변경 이력 표에 한 줄 |
| 운영 배포 | 배포 기록 하나(`개발/운영/배포/`, 개발 규약 7절) |

소규모·1인 프로젝트는 배포 기록 대기 목록, 기능 문서 같은 것을 줄일 수 있다. 어디까지 줄이는지는 프로젝트 개발 규약에 쓴다.

[CLAIM] Google도 설계 문서를 쓰지 말아야 할 때를 따로 정해 두고, 형식보다 프로젝트에 맞는 형태를 우선한다([Design Docs at Google](https://www.industrialempathy.com/posts/design-docs-at-google/)).

## 4. 문서 형식

양식 파일은 틀의 `양식/` 폴더 한 곳에만 두고, 처음 쓸 때 만든다. 모든 프로젝트가 같은 양식을 복사해 쓴다.

### 4.1 시스템 설계 (옵시디안 `개발/시스템 설계/`)

[FACT] Google 설계 문서의 뼈대는 맥락과 범위 → 목표와 비목표 → 실제 설계 → 검토한 대안 → 교차 관심사다([Design Docs at Google](https://www.industrialempathy.com/posts/design-docs-at-google/)). 이 틀은 그 뼈대의 "실제 설계"를 C4 그림과 arc42의 세 관점(구조·흐름·배포)으로 채운다.

1. 맥락과 범위: 기획서·제품 디자인 링크, 사용자, 연결되는 외부 시스템
2. 목표와 비목표
3. 제약: 법·약관·비용·인력
4. 설계
   1. 시스템 컨텍스트 그림(C4 1단계)
   2. 모듈 구성(C4 2단계): 모듈마다 저장소, 역할, 제공하는 약속
   3. 주요 흐름
   4. 데이터: 저장하는 것, 저장하지 않는 것, 보관 기간
   5. 배포·운영(인프라)
5. 교차 관심사: 보안·규정, 로깅·모니터링, 오류 처리, 개인정보
6. 검토한 대안과 버린 이유
7. 테스트 전략
8. 단계와 범위(MVP), 위험과 미결 사항
9. 관련 결정 기록 목록(옵시디안 `개발/결정/`과 모듈 저장소 `docs/adr/` 모두)

**한 파일에 다 넣지 않는다.** 시스템 설계는 폴더로 만든다.

- 입구 문서 `시스템 설계.md`는 위 1~9절 순서를 지킨다. 맨 위에 문서 지도(폴더 트리)를 두고, 1·2절, 4.1 컨텍스트 그림, 6·8·9절은 입구에 직접 쓴다. 나머지 절은 영역 폴더의 문서로 나누고 입구에서 링크한다.
- 폴더 이름은 1.1절의 영역 이름을 쓴다.

| 절 | 위치 |
|---|---|
| 3 제약(법·약관), 5 보안·개인정보 | `보안·규정/` |
| 4.2 모듈 구성, 7 테스트 전략 | `애플리케이션/` |
| 4.3 주요 흐름(여러 모듈이나 외부 시스템을 가로지름, 흐름 하나에 시퀀스 그림 하나) | `애플리케이션/흐름/` |
| 1 외부 시스템 연동(받는 쪽): 시스템 하나에 문서 하나. 스펙 요약 → 샘플 호출 결과 → 확인 항목 → 장애 시 동작, 환경별 주소와 키 "위치" | `애플리케이션/외부 연동/` |
| 모듈 내부 구조(C4 3단계) | 저장소가 정본이다. 루트 `README.md`가 입구(기술 선택, 폴더 지도, 언어별 규약이 없을 때의 코드 규칙)이고, 코드 폴더(레이어·모듈)마다 `README.md`를 하나씩 둔다. 모듈 간 약속(API)은 `docs/interfaces/`에 둔다. 옵시디안 `애플리케이션/모듈 구성.md`에는 저장소 링크만 남긴다. 저장소를 만들기 전에는 `애플리케이션/<모듈>/`에 초안으로 쓰고, 저장소를 만들 때 옮긴 뒤 지운다 |
| 4.4 데이터 | `데이터/` |
| 4.5 배포·운영(인프라), 환경 표(개발·검증·운영의 주소, 접속 방법, 배포 방법, 외부 연동 환경별 주소. 키는 위치만) | `기술·인프라/` |
| 5 로깅·모니터링·오류 처리, SLO 설계 | `운영/` |

- 내용이 없는 영역 폴더는 만들지 않는다(0절 원칙 1). 입구의 해당 절에 "미정"과 정할 시점만 적는다.
- 시스템 설계 안의 `운영/`은 운영 설계(오류 처리·로깅·SLO)다. 실제 운영 절차는 `개발/운영/`에 둔다.
- 나눈 문서도 frontmatter에 따르는 틀 버전(`standard_version`)과 입구 문서 링크(`related`)를 적는다.
- **현행 설계는 문서 하나.** 버전별 페이지(`시스템 0.5`, `0.6`…)를 만들지 않는다. 바꾸는 안은 ADR(상태 `제안`)로 쓰고, 승인되면 현행 문서를 고친다. 이전 모습은 Git 이력과 ADR로 본다.

### 4.2 결정 기록(ADR)

### 4.3 도메인과 기능

오래 남는 지식은 **도메인** 단위로, 진행 중인 일은 **기능(에픽)** 단위로 쓴다. 기능은 끝나는 단위라 기능 문서를 현행 기준으로 쓰면 끝난 문서가 쌓여 무엇이 지금 동작인지 알 수 없게 된다(도메인 설계 문서가 티켓 이름 문서로 바뀌며 무너지는 흔한 사례, 2.6절 근거).

| 층 | 무엇 | 위치 | 언제 고치나 |
|---|---|---|---|
| 도메인 목록 | 도메인 이름·책임·담당 모듈 저장소·현행 명세 경로 | 옵시디안 `개발/도메인/도메인 목록.md` | 셋업 때 만들고, 도메인을 새로 만들거나 합칠 때(결정 기록) |
| 현행 명세 | 도메인마다 지금 동작과 수용 기준(코드 기준 정본) | 저장소 `docs/specs/<도메인>.md` | 동작을 바꾸는 PR이 같은 PR에서 |
| 도메인 문서 | 도메인마다 지금 규칙·동작·API·데이터 요약과 변경 이력. 문서만 보고 도메인을 파악하는 정리본 | 옵시디안 `개발/도메인/<도메인>/<도메인>.md`. 정책·화면은 `기획/<도메인>/`, 디자인은 `제품 디자인/<도메인>/` | 기능 완료 때 코디네이터가 |
| 기능 문서 | 에픽 하나의 무엇·왜·스토리·영향 도메인·초안·하위 작업 | 옵시디안 `기능/<에픽 키> <기능>/<기능>.md` | 기능이 끝나면 고치지 않는다(이력) |
| 기능 목록 | 마일스톤별 에픽·상태(예정/진행/완료)·담당 | 옵시디안 `기능/기능 목록.md` | 상태가 바뀔 때 코디네이터가 |

- **도메인 나누기(셋업)**: 프로젝트 시작 때(5절 체크리스트 3번) 도메인 목록을 쓰고 도메인마다 `개발/도메인/<도메인>/<도메인>.md`([[30 Areas/Development Standard/양식/도메인 문서 양식|도메인 문서 양식]])를 만든다. `기획/`·`제품 디자인/` 하위 폴더와 저장소 `docs/specs/`도 같은 도메인 이름을 쓴다. 기능은 바뀌어도 도메인 이름은 쉽게 바꾸지 않는다.
- **정본**: 코드 동작은 저장소 현행 명세가 정본이다. 도메인 문서는 정리본이라 세부를 베끼지 않고 요약하고 저장소 명세에 링크한다. 둘이 다르면 저장소가 맞고, 다음 기능 완료 때 맞춘다.
- **Jira 단위**: 마일스톤 → 에픽(기능) → 스토리(사용자 가치 하나, 예: "회원은 책을 예약할 수 있다") → 하위 작업(결과물 하나: 기획·디자인·개발·QA). 스토리를 직무별(기획 스토리, 개발 스토리)로 나누지 않는다. **개발 하위 작업 하나 = PR 하나 = `ticket-workflow` 하나**라서, 저장소·모듈이 다르면 개발 하위 작업이 여럿이 된다. 버그는 스토리와 같은 층이다.
- **에픽 키**: Jira 에픽 키(`BOOK-10`). Jira가 없으면 `E-<번호>`. 에픽이 기획·디자인·개발을 함께 묶으므로 `기능/`은 프로젝트 최상위에 둔다.
- **기능 폴더**: 스토리마다 폴더를 만들지 않는다(경로가 깊어짐). 개발 하위 작업 폴더는 에픽 폴더 바로 아래 두고, 속한 스토리는 문서 앞머리 `story:`에 적는다.

  ```
  기능/BOOK-10 대여 예약/
  ├── 대여 예약.md            ← 기능 문서(스토리 표, 하위 작업 표)
  ├── 기획/ 디자인/            ← 이번 변경분 초안
  ├── BOOK-14 예약 API/       ← 개발 하위 작업(ticket-workflow 산출물)
  └── BOOK-15 예약 화면 구현/
  ```

- **진행 중 초안**: 기획·디자인 하위 작업은 이번 변경분을 기능 폴더 `기획/`·`디자인/`에 쓴다. 현행 `기획/<도메인>/`·`제품 디자인/<도메인>/`은 완료 때 반영한다. 아직 배포되지 않은 동작이 현행 문서에 섞이지 않게 하기 위해서다.
- **완료(반영 단계)**: 하위 작업이 모두 병합되고 QA가 수용 기준을 확인하면 코디네이터가 ① 기능 폴더의 기획·디자인 초안을 `기획/<도메인>/`·`제품 디자인/<도메인>/`에 반영하고, ② 이번에 바뀐 저장소 현행 명세를 `개발/도메인/<도메인>/` 도메인 문서에 정리하고 변경 이력에 한 줄(날짜·에픽 키)을 남기고, ③ 기능 문서의 완료 칸과 ④ 기능 목록 상태를 바꾼다. 반영 전에는 완료가 아니다. 배포 기록의 포함 티켓 표에 기능 열을 적는다.
- **새 기능 vs 기존 기능**: 새 동작이 생기면 새 에픽. 동작이 그대로인 개선·버그 수정은 관련 에픽에 넣거나, 마일스톤마다 하나 두는 유지보수 에픽에 넣는다.
- 저장소가 없는 단계(설계 중)의 도메인 명세 초안은 `시스템 설계/애플리케이션/<모듈>/`에 두고, 저장소가 생기면 옮긴다(4.1절).

### 4.4 제품 디자인 문서 (옵시디안 `제품 디자인/`)

사용자와 상황, 사용자 흐름, 화면·메시지 목록과 상태, 카피 원칙과 금지 표현, 브랜드(이름·톤), 디자인 시스템, Figma 링크.

- **정책서**: 정책 하나에 문서 하나(권한, 알림 조건, 다국어, 시간대 표시 등 여러 화면에 걸리는 규칙). 관련 화면 설계를 링크한다.

## 6. 팀 표준 기본값

**기술**
- 언어는 Python 3.15이고, 모듈 저장소마다 uv 기반 `.venv`를 쓴다.
- 표준 라이브러리를 우선한다. 외부 패키지는 추가 이유를 남기고 버전을 고정한다.
- 아키텍처는 헥사고날 구조(2.4절)를 따른다.
- 도구 기본값(셋업 질문의 권장안, 프로젝트가 바꿀 수 있다): 포맷·린트 `ruff`, 타입 `pyright`, 아키텍처 테스트 `import-linter`, 커밋 훅 `pre-commit`(ruff·gitleaks), 테스트 `pytest`, 의존성 `uv.lock` + `pip-audit`, DB PostgreSQL + Alembic, 배포는 서버가 태그를 가져오는 `deploy/deploy.sh <태그>`. 클라이언트는 iOS Swift·SwiftUI + `swift format`, 웹 TypeScript + Biome.

**작업 방식**
- Git은 gitflow를 쓴다(`main` 운영, `develop` 개발, `feature/`·`release/`·`hotfix/`). 작업은 작게 나눠 합친다. 세부 규칙은 [[30 Areas/Development Standard/개발 규약|개발 규약]] 5절.
- 버전 태그는 SemVer `vMAJOR.MINOR.PATCH`: DB·API가 이전과 호환되지 않게 바뀌면 MAJOR, 호환되는 기능 추가가 든 운영 배포는 MINOR, 그 외 운영 배포(수정·최적화·설정·문서)와 hotfix는 PATCH. 이미 붙은 태그는 옮기지 않는다(개발 규약 5절).
- CI는 GitHub Actions로 돌리되, 요금·사용 시간 부족으로 실패하면 같은 검사 스크립트(`scripts/check.sh`)의 로컬 통과 결과로 대신한다(개발 규약 6절).
- 기능은 설정으로 켜고 끌 수 있게 만든다.
- 모든 반영에는 되돌리는 방법이 있어야 한다.
- 리뷰는 AI 리뷰 + 사람 리뷰다. 코디네이터(AI)가 1차 리뷰하고 사람(프로젝트 책임자·개발 리더)이 승인한 PR만 병합한다(사용자가 병합을 일임한 경우는 그대로). 체크 항목은 [[30 Areas/Development Standard/개발 규약/코드 리뷰|코드 리뷰]] 규약을 쓴다.
- 완료 기준: 테스트 통과, 기능 문서의 수용 기준 확인, 현행 명세(`docs/specs/<도메인>.md`) 갱신, 기능 완료 때 도메인 문서 반영

**품질**
- 틀리기 쉬운 로직(파서, 판정 규칙, 돈 계산, 서명·보안)은 테스트를 반드시 둔다.
- 자동 검사(CI)에서 테스트, 패키지 취약점, 비밀정보 노출을 확인한다.

**보안·규정**
- 비밀정보는 `$SECRETS_ROOT/<프로젝트>/`에 두고, 키는 명의자가 직접 넣는다.
- AI에게 실제 키와 계정 정보를 보여 주지 않는다.
- 권한은 필요한 만큼만 준다.
- 개인정보는 수집하지 않는 것을 기본으로 하고, 수집하면 보관 기간과 삭제 방법을 정한다.
- 프로젝트별 법·약관 점검표를 둔다.

**운영**
- 로그는 구조화된 형식으로 남긴다.
- SLO는 2~3개만 정하고, 목표가 빠르게 깨질 때 알린다. [CLAIM] 고정 임계값보다 목표 소진 속도 기반 알림이 낫다는 실무 권고가 있다([OneUptime](https://oneuptime.com/blog/post/2026-02-06-slo-monitoring-opentelemetry-metrics/view)).
- 알림은 운영자 메신저로 보낸다.
- 비용 표와 백업을 둔다.

**AI 협업**
- 모듈 저장소 루트 입구 문서는 `CLAUDE.md` 하나이고, 네 가지만 적는다: 따르는 틀 버전과 경로, 프로젝트 문서 경로(옵시디안), 주요 명령, 이 모듈 고유 규칙과 사람 확인 지점.
- 사람 확인 지점: 운영 배포, 비밀정보, 외부로 나가는 발송, 돈, 데이터 삭제
- AI가 만든 결과의 책임은 리뷰한 사람에게 있다.
- [INFERENCE] 이 맥에서 도는 AI는 옵시디안 경로를 직접 읽을 수 있다. 다른 곳에서 도는 AI와 자동 검사(CI)는 저장소만 읽으므로, 코드와 같이 바뀌는 문서는 반드시 저장소에 둔다.

**틀 배포**
- 다른 사람이 쓰도록 이 틀과 `project-setup` 스킬을 플러그인 `project-standard-kit`으로 묶어 배포한다. 배포본은 이 폴더에서 만든 사본(개인 경로·이름·변경 이력 제거)이고, 버전은 이 문서 `version`을 따른다.
- 이 폴더를 고치면 배포본이 자동으로 다시 만들어져 공개 저장소에 올라간다(원본 저장소의 CI가 빌드하고, 개인 정보가 남으면 실패해 올리지 않는다).
