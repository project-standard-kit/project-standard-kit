# 티켓 진행 방식 (코디네이터–작업자)

> [[30 Areas/Development Standard/개발 규약|개발 규약]] 13절. 버전과 변경 이력은 개발 규약 입구 문서에 둔다.

> 모든 프로젝트에 공통으로 쓰는 방식이다. 프로젝트에 맞게 바꾸는 점은 프로젝트 `개발 규약`에 쓴다.

- **코디네이터:** 프로젝트를 여는 메인 세션이다. 티켓을 나눠 주고, 작업자 PR을 리뷰해 `develop`에 squash 병합하고, 티켓 상태·릴리스·배포 요청을 맡는다. 티켓 단위 구현은 직접 하지 않는다(한 줄 설정·핫픽스 같은 작은 수정은 예외).
- **작업자:** 티켓마다 독립된 작업 공간(새 워크트리)과 그 안의 에이전트 하나다. 작업 공간 도구·에이전트 모델·effort는 프로젝트 셋업 때 정한다(예: Orca 워크스페이스, 중간 크기 모델 + effort medium). 겹치는 파일을 건드리는 티켓은 같은 작업 공간에서 차례로 하거나 의존 순서를 정한다.
- **절차:** 작업자는 `ticket-workflow` 스킬 7단계(분석 → 설계 → 구현 문서 → 구현 → 리뷰 문서 → PR → 셀프 리뷰)로 진행한다. 분석·계획은 `ticket-planner`, 독립 코드 리뷰는 `ticket-reviewer` 서브에이전트가 맡는다. 작은 개발 Task(한 모듈, 파일 1~3개, 계약·보안·데이터 변경 없음)는 **경량 경로**(planner 생략, 설계·구현 문서 한 장, Sonnet 리뷰만, 7단계 셀프 리뷰 생략)로 하고, 애매하면 전체 경로로 한다. 단계는 자동 승인으로 넘어가고, 제품 결정이 필요하면 코디네이터에게 묻고 코디네이터가 모아 사용자에게 묻는다.
- **티켓 번호:** Jira 프로젝트가 있으면 그 번호, 없으면 저장소 번호(`BOOK-78`처럼)를 쓴다. 브랜치는 `feature/<번호>-<설명>`, 커밋은 `feat(<번호>): …`다.
- **기능과 티켓:** Jira 단위는 에픽(기능) → 스토리(사용자 가치) → 하위 작업(결과물 하나: 기획·디자인·개발·QA)이다(표준 틀 4.3절). 여기서 "티켓"은 **개발 하위 작업**이고, 하나가 PR 하나이며 이것만 위 `ticket-workflow` 절차로 진행한다. 코디네이터는 기능을 시작할 때 `기능/<에픽 키> <기능>/<기능>.md`([[30 Areas/Development Standard/양식/기능 문서 양식|기능 문서 양식]])와 `기능/기능 목록.md` 상태를 만들고, 기능이 끝나면 반영 단계(도메인 문서·`기획/`·`제품 디자인/`)를 마친 뒤 `완료`로 바꾼다(표준 틀 4.3절).
- **현행 명세 갱신은 PR 완료 조건이다.** 동작을 바꾸는 티켓은 같은 PR에서 저장소 `docs/specs/<도메인>.md`를 고친다. 옵시디안 도메인 문서는 작업자가 고치지 않고, 기능 완료 때 코디네이터가 정리한다.
- **산출물:** 옵시디안 프로젝트 `기능/<에픽 키> <기능>/<하위 작업 키> [요약]/` 아래(스토리 폴더는 만들지 않고 문서 앞머리 `story:`에 스토리 키) `설계 문서.md`, `구현 문서.md`, `리뷰 문서.md`, `adr/`. 결정 기록은 저장소 `docs/adr/`에도 같은 번호로 둔다.
- **작업자는 PR까지만 한다.** 병합·릴리스·배포는 코디네이터가 하고, 운영 배포·비밀정보·외부 발송·돈·데이터 삭제는 [[30 Areas/Development Standard/개발 규약/AI 협업|AI 협업]]의 사람 확인 지점 그대로 사용자 확인을 받는다. 작업자에게 운영 배포·운영 DB 쓰기·운영 프로세스 재시작을 맡기지 않는다.
- **개발이 아닌 하위 작업**(기획, 디자인, 문서 정리, QA, 운영, 사람이 할 일)은 7단계 없이 진행한다. 기획·디자인 결과물은 기능 폴더 `기획/`·`디자인/`에 이번 변경분 초안으로 쓰고, 현행 `기획/<도메인>/`·`제품 디자인/<도메인>/`에는 기능 완료 때 반영한다.
- **감시:** 코디네이터는 작업자를 폴링하지 않는다. 작업 공간 도구가 완료·질문·중단을 알려 주면 그때 처리하고, 멈춘 작업자는 깨우거나 다시 시작한다.
- **프로젝트에 맞게 바꾸는 점**(예: 저장소 호스트, 빌드 검증 명령, 실기기 시험)은 프로젝트 `개발 규약`에 쓴다. 예: `ticket-workflow`의 GitLab 부분은 `gh pr create --base develop`, 검증은 `scripts/check.sh`로 바꾼다.
