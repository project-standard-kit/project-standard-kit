# 아키텍처 레이어

> [[30 Areas/Development Standard/개발 규약|개발 규약]] 1절. 버전과 변경 이력은 개발 규약 입구 문서에 둔다.

## 공통 규칙

- 폴더 구조와 의존 방향은 [[30 Areas/Development Standard/프로젝트 표준 틀|표준 틀]] 2.4절이 정본이다.
  - `domain`은 프로젝트의 다른 레이어를 쓰지 않는다. 표준 라이브러리(`logging` 포함)는 쓸 수 있고, 프레임워크·DB·HTTP 라이브러리는 모른다.
  - `app`은 `domain`과 표준 라이브러리만 쓴다. 바깥에 기대는 것(시각, 저장소, 외부 호출)은 포트로 정의하고 구현은 `platform`·`adapters`가 맡는다.
  - `adapters`는 `app`·`domain`·`platform`을 쓴다.
  - `platform`은 `adapters`와 진입점(`main`)이 쓴다. `app`·`domain`이 `platform`을 직접 import하는 것은 금지다.
  - 시각, 로그 출력 설정, 외부 연결은 `platform`/`main`이 만들어 주입한다. 시각은 호출자가 `now` 인자로 넘긴다.
  - 전부를 아는 곳은 진입점(`main`) 하나다.
- 도메인이 여럿이면 `domain`·`app` 아래를 도메인 이름으로 나눈다(`domain/<도메인>/`). 다른 도메인의 내부를 직접 가져다 쓰지 않고, 그 도메인 `app`이 공개한 함수·포트만 쓴다.
- **의존 방향은 사람 리뷰가 아니라 자동 검사로 지킨다(아키텍처 테스트).** CI 검사 진입점([[30 Areas/Development Standard/개발 규약/CI|6절]])에서 돌고, 위반이면 실패한다.
- 검사는 직접 import뿐 아니라 간접 import, `domain`의 외부 패키지 사용도 잡아야 한다.

## 프로젝트 셋업 때 정할 것

모듈 저장소마다 [[30 Areas/Development Standard/양식/프로젝트 개발 규약 양식|프로젝트 개발 규약]] 1절에 적는다.

| 항목 | 정할 내용 |
|---|---|
| 레이어 이름 | 위 다섯 자리를 이 모듈에서 무엇이라 부르나(언어 관례에 맞게) |
| 검사 도구 | 아키텍처 테스트 도구와 설정 파일 위치 |
| `domain` 금지 목록 | `domain`이 쓰면 안 되는 외부 패키지(이 모듈의 프레임워크·DB·HTTP 라이브러리) |
| 예외 | 규칙을 벗어나는 곳의 위치와 이유. 없으면 "없음" |

## 예

- Python: `import-linter`의 `layers` 계약(위 → 아래만 허용, `|`로 묶으면 서로 독립)과 `forbidden` 계약(`domain` → 외부 패키지 금지). [FACT] 2.16이 Python 3.15에서 동작하고 레이어 위반과 외부 패키지 사용을 모두 잡는 것을 2026-11-07 확인했다.
- Java·Kotlin: ArchUnit. TS: dependency-cruiser. Swift: 모듈(SPM 타깃)을 나눠 컴파일러가 막게 한다.
- 도구가 없으면 import를 읽어 방향을 검사하는 테스트 하나로 대신한다(예: `tests/test_architecture.py`).
