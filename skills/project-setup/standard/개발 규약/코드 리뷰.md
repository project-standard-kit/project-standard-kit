# 코드 리뷰와 PR

> [[30 Areas/Development Standard/개발 규약|개발 규약]] 15절. 버전과 변경 이력은 개발 규약 입구 문서에 둔다.

## 1. 공통 규칙

**PR 크기와 단위**
- PR 하나 = 개발 하위 작업 하나([[30 Areas/Development Standard/개발 규약/티켓 진행 방식|13절]]).
- 작게 만든다. 바뀐 줄이 400줄(생성 파일·잠금 파일 제외)을 넘으면 나눌 수 있는지 먼저 본다.
- 구조 변경(리팩터링)과 동작 변경을 한 PR에 섞지 않는다. 의존성 업데이트도 따로.

**PR 설명** (제목은 커밋 형식, [[30 Areas/Development Standard/개발 규약/Git과 버전|5절]])
1. 무엇을, 왜: 티켓 키와 링크, 한두 문장
2. 확인 방법: 실행한 검사와 결과, 화면 변경이면 스크린샷
3. 위험과 되돌리기: 스키마·API·설정 변경 여부, 되돌리는 방법
4. 갱신한 문서: 현행 명세, `docs/interfaces/` 등([[30 Areas/Development Standard/개발 규약/문서 갱신|11절]])

**리뷰 전에**
- 검사 진입점([[30 Areas/Development Standard/개발 규약/CI|6절]])을 통과한 뒤에 리뷰를 요청한다. 형식·스타일은 리뷰에서 다루지 않는다(도구 몫).
- 작성자가 먼저 자기 diff를 한 번 읽는다.

**리뷰어가 보는 것** (도구가 못 잡는 것)
- 요구와 맞나: 수용 기준을 채우나, 범위 밖 변경이 섞였나
- 경계: 레이어·도메인 경계를 지키나, 범위가 다른 API를 섞었나
- 실패할 때: 오류 처리, 타임아웃, 재시도, 데이터가 반쯤 바뀐 채 남는 경우
- 보안: 권한 확인, 입력 검증, 비밀정보·개인정보([[30 Areas/Development Standard/개발 규약/보안|14절]])
- 호환: DB·API 변경이 이전 버전과 같이 돌아가나
- 테스트: "반드시 테스트할 것"과 수용 기준이 덮였나
- 이름: 도메인 용어와 같은가

**리뷰 방식**
- 리뷰는 AI 리뷰 + 사람 리뷰다. AI 리뷰(티켓 방식에서는 코디네이터의 1차 리뷰)가 먼저 돌고 사람이 최종 승인한다. 사람이 승인한 PR만 병합한다. 사용자가 병합을 일임한 경우는 그대로 병합한다([[30 Areas/Development Standard/개발 규약/티켓 진행 방식|13절]]). 결과의 책임은 승인한 사람에게 있다.
- 댓글은 무게를 붙인다: `필수:` 고쳐야 합침, `제안:` 작성자가 판단, `질문:` 이해 확인.
- 하루 안에 첫 리뷰를 한다. 의견이 갈리면 짧게 이야기하고, 결정이면 결정 기록으로 남긴다.
- 합치기는 squash. 합친 브랜치는 지운다.

## 2. 프로젝트 셋업 때 정할 것

[[30 Areas/Development Standard/양식/프로젝트 개발 규약 양식|프로젝트 개발 규약]] 15절에 적는다.

| 항목 | 정할 내용 |
|---|---|
| 리뷰어 | 사람 리뷰어, AI 리뷰 도구 |
| 승인 수 | 합치는 데 필요한 승인 |
| PR 양식 위치 | 저장소 PR 템플릿 경로 |

팀 기본값: 사람 승인 1명 + AI 리뷰, 체크 항목은 이 문서 1절, 템플릿은 `.github/pull_request_template.md`.
