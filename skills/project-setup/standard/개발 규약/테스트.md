# 테스트

> [[30 Areas/Development Standard/개발 규약|개발 규약]] 8절. 버전과 변경 이력은 개발 규약 입구 문서에 둔다.

## 1. 공통 규칙

**층마다 다르게**

| 대상 | 테스트 | 외부 의존 |
|---|---|---|
| `domain` | 단위 테스트. 가장 많이, 빠르게 | 없음 |
| `app` | 유스케이스 테스트 | 포트를 가짜(fake)로 |
| `adapters` | 통합 테스트 | 실제 DB(테스트용 인스턴스), 외부 API는 기록해 둔 실제 응답 |
| 핵심 사용자 흐름 | E2E 몇 개만 | 테스트 환경 |

**반드시 테스트할 것:** 파서, 판정 규칙, 돈 계산, 규정·문구 점검, 서명·인증·권한, 상태 전이.

**쓰는 법**
- 테스트 하나는 동작 하나를 본다. 이름은 `test_<동작>_<조건>_<결과>`(예: `test_reserve_when_book_taken_raises_conflict`).
- 준비 → 실행 → 확인 순서로 쓴다.
- 구현 내부가 아니라 바깥에서 보이는 동작을 확인한다. 리팩터링으로 깨지는 테스트는 잘못 쓴 것이다.
- 테스트는 결정적이어야 한다. 시각·난수·순서에 기대지 않는다(시계와 난수는 주입한다).
- 테스트가 실제 외부 서비스를 부르지 않는다. 외부 응답은 저장해 둔 실제 응답(`tests/fixtures/`)으로.
- 테스트 폴더는 소스와 같은 구조로 둔다.

**버그와 불안정한 테스트**
- 버그를 고칠 때는 그 버그를 재현하는 테스트를 먼저 쓰고, 실패를 확인한 뒤 고친다.
- 가끔 실패하는 테스트는 바로 격리(건너뛰기 표시 + 티켓 키)하고 일주일 안에 고치거나 지운다. 재실행으로 넘기지 않는다.

**커버리지**
- 숫자 목표를 걸지 않는다. 위 "반드시 테스트할 것"과 수용 기준이 테스트로 덮였는지를 리뷰에서 본다.

**사람 확인이 필요한 것**
- 화면 조작과 LLM 에이전트 흐름은 단위 테스트 대신 테스트 환경(테스트 방, 테스트 계정)에서 돌리고, 로그와 스크린샷으로 확인한다.

**완료 기준:** 테스트 통과, 기능 문서의 수용 기준 확인, 현행 명세(`docs/specs/<도메인>.md`) 갱신(표준 틀 4.3절).

## 2. 프로젝트 셋업 때 정할 것

[[30 Areas/Development Standard/양식/프로젝트 개발 규약 양식|프로젝트 개발 규약]] 8절에 적는다.

| 항목 | 정할 내용 |
|---|---|
| 도구 | 테스트 도구, 실행 명령 |
| 통합 테스트 DB | 테스트용 DB를 어떻게 띄우나 |
| E2E 대상 | 핵심 흐름 목록(3~5개) |
| 이 프로젝트의 필수 대상 | 공통 목록 외에 반드시 테스트할 것 |

## 3. 예

팀 기본값: `pytest`, `tests/`는 `src/`와 같은 구조.
