# CD (배포)

> [[30 Areas/Development Standard/개발 규약|개발 규약]] 7절. 버전과 변경 이력은 개발 규약 입구 문서에 둔다.

## 1. 공통 규칙

- **배포는 명령 하나로 재현된다.** 사람이 서버에서 손으로 단계를 밟지 않는다. 명령은 태그를 받는다.
- **배포하는 것은 태그다.** 브랜치나 작업 중 코드를 운영에 올리지 않는다. 의존성은 잠금 파일 그대로 설치한다.
- **되돌리기는 이전 태그로 같은 명령을 다시 돌리는 것이다.** 그래서 스키마 변경은 이전 버전 코드와도 돌아가게 만든다([[30 Areas/Development Standard/개발 규약/DB|DB]]).
- 순서: DB(스키마 변경) → 백엔드 → 프론트·앱. 각 단계 뒤 상태 확인(`/health`)을 한다.
- 운영 배포는 사람이 실행한다([[30 Areas/Development Standard/개발 규약/AI 협업|AI 협업]]의 사람 확인 지점).
- 서버로 들어오는 길은 최소로 연다. 가능하면 서버가 태그를 가져가는 방식(pull)으로 한다.
- 운영 설정은 저장소 `deploy/`에 두고, 서버에서 손으로 고치지 않는다(비밀정보만 저장소 밖).
- **배포 기록.** 운영 배포 1회 = 문서 1개: 옵시디안 프로젝트 `개발/운영/배포/YYYY-MM-DD <정기·긴급>.md`(같은 날 같은 종류가 둘이면 둘째에 `-2`: `YYYY-MM-DD 긴급-2.md`). [[30 Areas/Development Standard/양식/배포 기록 양식|배포 기록 양식]]을 복사해 쓴다. 모듈마다 태그가 다르면 `version`에 모듈별로 적는다.
- **정기·긴급.** 정기 배포는 정한 주기로 `release/`에서, 긴급 배포는 `hotfix/`에서 한다. 다음 정기 배포에 넣을 티켓은 `개발/운영/배포/대기 목록.md`에 모은다.
- 배포 후 30분은 오류 알림과 로그를 본다.

## 2. 프로젝트 셋업 때 정할 것

[[30 Areas/Development Standard/양식/프로젝트 개발 규약 양식|프로젝트 개발 규약]] 7절에 적는다. 인프라 자체(서버, 환경, 실행 방식)는 시스템 설계 `기술·인프라/`에 쓴다.

| 항목 | 정할 내용 |
|---|---|
| 방식과 명령 | pull / push, 배포 명령 |
| 환경 | 환경 이름(`dev`·`test`·`prod` 중), 환경별 위치(인프라 문서 링크) |
| 정기 주기·시간대 | 언제 배포하나, 피하는 시간 |
| 멈춤 방법 | 배포 중 문제가 생기면 어떻게 멈추나 |
| 앱 배포 | 앱 스토어 등 다른 경로가 있으면 그 절차 |

## 3. 예

팀 기본값: 서버가 태그를 가져와 `uv sync --frozen` → 스키마 변경 적용 → 서비스 재시작을 하는 `deploy/deploy.sh <태그>`.
