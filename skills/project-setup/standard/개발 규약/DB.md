# DB

> [[30 Areas/Development Standard/개발 규약|개발 규약]] 4절. 버전과 변경 이력은 개발 규약 입구 문서에 둔다.

## 1. 공통 규칙

**소유**
- 테이블은 도메인 하나가 소유한다. 다른 도메인의 테이블을 직접 읽거나 쓰지 않고 그 도메인의 `app`을 거친다. 도메인 사이 외래 키는 되도록 걸지 않고 ID만 들고 있는다.
- DB 접근은 `adapters`에서만 한다([[30 Areas/Development Standard/개발 규약/아키텍처 레이어|1절]]).

**이름** (관계형 DB 기준)

| 대상 | 규칙 | 예 |
|---|---|---|
| 테이블 | `snake_case` 복수형. 도메인이 여럿이면 스키마 또는 접두어로 도메인 구분 | `rental.reservations` |
| 기본 키 | `id` | |
| 외래 키 컬럼 | `<참조 단수>_id` | `book_id` |
| 시각 | `created_at`, `updated_at`(모든 테이블), 시간대 포함 타입(UTC) | `timestamptz` |
| 참·거짓 | `is_`·`has_` | `is_active` |
| 인덱스 | `ix_<테이블>_<컬럼>` | `ix_reservations_book_id` |
| 유니크 | `uq_<테이블>_<컬럼>` | |
| 외래 키 제약 | `fk_<테이블>_<컬럼>` | |
| 체크 | `ck_<테이블>_<조건>` | |

**데이터**
- 돈은 정수 최소 단위, 상태는 정해진 값 목록(체크 제약 또는 enum).
- 필수 값은 `NOT NULL`. 규칙으로 막을 수 있는 건 앱보다 DB 제약으로도 막는다(유니크, 외래 키, 체크).
- 삭제 정책을 테이블마다 정한다: 진짜 삭제 / 소프트 삭제(`deleted_at`). 소프트 삭제면 조회 기본값에서 뺀다.
- 보관 기간이 있는 데이터는 지우는 예약 작업을 같이 만든다.

**스키마 변경**
- 마이그레이션 도구로만 한다. 운영 DB를 손으로 바꾸지 않는다.
- 앞으로만 간다. 되돌리기는 새 변경으로.
- 모든 변경은 이전 버전 코드와 같이 돌아가야 한다(배포 되돌리기가 가능하도록). 깨는 변경은 넓히기 → 옮기기 → 좁히기(expand/contract)로 여러 배포에 나눈다.
- 큰 테이블의 인덱스 추가·데이터 옮기기는 잠금을 피하는 방법으로, 배포와 분리해서 한다.

**쿼리와 트랜잭션**
- 트랜잭션 경계는 `app`의 유스케이스 하나다. 트랜잭션 안에서 외부 HTTP 호출을 하지 않는다.
- 목록 조회는 항상 상한(`LIMIT`)이 있다. 반복문 안에서 쿼리를 날리지 않는다(N+1).
- 문자열로 SQL을 이어 붙이지 않는다. 파라미터 바인딩만.

**권한**
- 역할을 나눈다: 앱용(읽기·쓰기), 변경용(스키마), 백업용(읽기). 앱 역할은 스키마를 바꿀 수 없다.

## 2. 프로젝트 셋업 때 정할 것

[[30 Areas/Development Standard/양식/프로젝트 개발 규약 양식|프로젝트 개발 규약]] 4절에 적는다.

| 항목 | 정할 내용 |
|---|---|
| DB 종류와 위치 | DBMS, 어디서 도나(시스템 설계 `기술·인프라/`) |
| 마이그레이션 도구 | 도구, 파일 위치 |
| 도메인 구분 | 스키마로 / 접두어로 |
| 역할 | 역할 이름과 권한 |
| 백업 | 주기와 위치(인프라 문서 링크) |
