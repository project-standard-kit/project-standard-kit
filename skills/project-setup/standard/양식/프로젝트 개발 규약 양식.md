# <프로젝트> 개발 규약

> 따르는 틀: [[30 Areas/Development Standard/개발 규약|개발 규약]] v0.15, [[30 Areas/Development Standard/프로젝트 표준 틀|프로젝트 표준 틀]] v0.16

## 이 양식 쓰는 법

- 프로젝트 셋업(표준 틀 5절 4단계)에서 `project-setup` 스킬이 아래 **질문지**를 순서대로 프로젝트 리더에게 묻는다. 질문마다 권장안을 먼저 보여 주고, 리더는 고르기만 한다. 권장안은 기획서·시스템 설계 1~3절(규모, 예산, 사용자)을 보고 정하고, 근거가 없으면 팀 기본값([[30 Areas/Development Standard/프로젝트 표준 틀|표준 틀]] 6절)을 쓴다.
- 답을 모으면 스킬이 아래 **만들어지는 것**을 한 번에 만든다: 이 문서, 인프라 구성도가 들어간 시스템 설계, 저장소 뼈대와 설정, CI, 배포 스크립트.
- 결과 문서는 프로젝트 `개발/<프로젝트> 개발 규약.md`이고 frontmatter에 따르는 틀 버전을 `standard_version`으로 적는다. 절 번호는 [[30 Areas/Development Standard/개발 규약|개발 규약]]과 같다. 틀을 그대로 따르는 절은 "틀 그대로"라고만 쓴다.
- 지금 못 정하는 것은 "미정 — 이유, 언제 정하나"로 남긴다. 설정 내용은 저장소에 두고 여기에는 위치와 결정만 쓴다.
- 리더가 고른 것은 결정 기록에 `승인`, 리더가 묻지 않고 넘긴 권장안은 `제안`으로 남긴다.

## 질문지

한 번에 4개까지 묻는다(묶음 = 한 번의 질문). 순서는 0 → A → B → C → D → F → E. 앞 묶음의 답으로 뒤 권장안이 바뀌고, 해당 없는 묶음은 건너뛴다(서버만이면 F, "개발만"이면 E3의 배포 세부).

### 묶음 0. 프로젝트 기본 (기획서가 있으면 거기서 후보를 뽑는다)

| ID | 질문 | 권장안 | 다른 선택지 |
|---|---|---|---|
| P1 | 프로젝트 이름(폴더·저장소 이름)과 한 줄 목표는? | 기획서의 이름·목표 | 직접 입력 |
| P2 | 주 사용자와 MVP 범위는? | 기획서에서 뽑은 MVP 기능 3~5개 | 더 좁게 / 더 넓게 |
| P3 | 도메인을 이렇게 나눌까? (이름, 책임, API 자원, 오류 코드 접두어 표를 보여 줌) | 기획에서 나눈 안 | 고쳐서 |
| P4 | 지금 개발을 시작할 단계인가, 기획·디자인부터인가? | 기획서·디자인이 있으면 개발 셋업까지 | 문서 뼈대만(저장소는 나중에) |

### 묶음 A. 규모와 바깥 (인프라 권장안의 근거)

| ID | 질문 | 권장안 | 다른 선택지 |
|---|---|---|---|
| A1 | 클라이언트와 서버 구성은? (대부분 짝이다) | 기획의 사용 화면에 맞춘 클라이언트 + 서버 1개 | 서버만(봇·API·배치) / 클라이언트만(서버 없음, 외부 서비스만) / 클라이언트 + 서버 여러 개 |
| A2 | 첫 6개월 예상 규모는? | 소규모(하루 사용자 1천 명 미만) | 중간(1만 명 안팎) / 큼 |
| A3 | 인프라 월 예산은? | 거의 0원(있는 장비·무료 등급) | 월 몇만 원 / 제한 없음 |
| A4 | 바깥에서 무엇이 들어오나? (여럿) | 웹훅만 | 공개 웹·API / 우리 앱 / 파트너 / 없음(내부 전용) |

### 묶음 B. 인프라

| ID | 질문 | 권장안 | 다른 선택지 |
|---|---|---|---|
| B1 | 운영 서버는 어디서 도나? | 소규모·0원이면 있는 장비(사무실·집의 상시 켜 둔 장비), 상시 공개면 무료 클라우드 VM(Oracle) | 관리형 플랫폼(Fly·Render) / 일반 클라우드(AWS·GCP) |
| B2 | 환경은 무엇을 쓰나? (개발 `dev` / 검증 `test` / 운영 `prod`) | 소규모면 `dev`(로컬) + `prod`, 외부 연동·결제·데이터 이전이 있으면 `dev` + `test` + `prod` | 개발만(운영은 첫 배포 전에 정함. 배포·백업·알림 질문은 그때 다시) |
| B3 | 서비스를 어떻게 띄우나? | 프로세스 관리자(launchd·systemd)로 자동 시작 | Docker Compose / 플랫폼에 맡김 |
| B4 | 외부에 어떻게 여나? | Cloudflare Tunnel(포트를 열지 않음) | 리버스 프록시 + 공인 IP / 열지 않음 |
| B5 | DB는? | PostgreSQL, 앱과 같은 서버 | SQLite / 관리형 PostgreSQL(Supabase·Neon) / 없음 |
| B6 | 백업은? | 매일 DB 덤프 → 로컬 백업 위치 + 바깥 한 곳, 분기마다 복원 연습 | 관리형 자동 백업 / 주 1회 |
| B7 | 고장 나면 어떻게 아나? | `/health` 외부 감시 + 오류 로그 → 운영자 메신저 알림 | 모니터링 도구(Grafana 등) / 나중에 |
| B8 | 비밀정보는 어디에? | 로컬 `$SECRETS_ROOT/<프로젝트>/`, 서버는 권한 600 env 파일 | 클라우드 비밀 관리자 / 플랫폼 비밀 변수 |

### 묶음 C. 코드 (모듈 언어마다)

| ID | 질문 | 권장안 | 다른 선택지 |
|---|---|---|---|
| C1 | 언어·런타임은? | Python 3.15 + uv | 모듈별 지정(Swift, TS 등) |
| C2 | 포맷·린트·타입 도구는? | 팀 기본값(ruff format·ruff check·pyright, 규칙 묶음 그대로) | 언어별 기본(Swift `swift format`, TS Biome + tsc) |
| C3 | 아키텍처 테스트 도구는? | `import-linter` | 언어별(ArchUnit, dependency-cruiser, SPM 타깃) / import 검사 테스트 |
| C4 | 커밋 훅과 에이전트 훅은? | `pre-commit`(포맷·린트 수정·gitleaks) + AI 작업자 수정 직후 포맷·린트 | 커밋 훅 없이 CI만 |

### 묶음 D. API와 데이터

| ID | 질문 | 권장안 | 다른 선택지 |
|---|---|---|---|
| D1 | 쓰는 API 범위는? (여럿) | A4 답에서 정함 | 퍼블릭 / 외부 연동 / 클라이언트 / 내부 / 관리자 |
| D2 | 범위별 인증은? | 클라이언트 토큰, 외부 연동 서명 검증, 관리자는 내부망 + 강한 인증 | 세션 쿠키 / API 키 / 서비스 인증(mTLS 등) |
| D3 | API 계약 형식은? | 프레임워크가 만드는 OpenAPI(태그 = 도메인) + 오류 코드 표 | Markdown 표만 |
| D4 | 개인정보를 수집하나? | 수집하지 않음 | 수집(항목·보관 기간·삭제 방법을 이어서 묻는다) |

### 묶음 F. 클라이언트 (A1에 클라이언트가 있을 때)

| ID | 질문 | 권장안 | 다른 선택지 |
|---|---|---|---|
| F1 | 클라이언트 종류는? (여럿) | 기획의 사용 환경대로(모바일 중심이면 iOS 앱) | 웹 / iOS / Android / 크로스플랫폼(React Native·Flutter) / 메신저 봇 |
| F2 | 클라이언트 기술은? | iOS는 Swift + SwiftUI, 웹은 TypeScript + React(Vite) | Next.js / Flutter / React Native |
| F3 | 서버와의 약속은 어떻게 맞추나? | 서버 OpenAPI → 클라이언트 API 코드 생성, 오류 코드별 처리는 한 곳 | 손으로 맞춤 / 같은 저장소(모노레포)에서 타입 공유 |
| F4 | 배포·버전 관리는? | 웹은 정적 호스팅(Cloudflare Pages), 앱은 TestFlight → App Store, 서버가 최소 지원 앱 버전을 알려 강제 업데이트 | 서버가 웹도 서빙 / 강제 업데이트 없음 |

클라이언트도 레이어(화면 → 상태·유스케이스 → 도메인 ← 데이터 어댑터)와 아키텍처 테스트, 공통 컨벤션(개발 규약 2절)을 그대로 따른다. 레이어 이름과 도구만 C2·C3에서 클라이언트 언어 기준으로 다시 묻는다. 환경별 API 주소는 클라이언트 설정(빌드 설정·환경변수)으로 나눈다.

### 묶음 E. 흐름과 배포

| ID | 질문 | 권장안 | 다른 선택지 |
|---|---|---|---|
| E1 | 원격 저장소와 티켓은? | GitHub 비공개 + Jira 프로젝트 키 | GitLab / 티켓 없이 `E-<번호>` |
| E2 | CI는? | GitHub Actions(PR마다) + 예산 예외 규칙 | 로컬 검사만 / 다른 CI |
| E3 | 배포 방식은? | 서버가 태그를 가져와 `deploy/deploy.sh <태그>`(pull) | CI가 서버로 밀기(push) / 플랫폼 자동 배포 |
| E4 | 정기 배포 주기와 리뷰는? | 주 1회 정기 + 긴급은 수시, 리뷰는 AI + 사람 1명 | 격주 / 필요할 때 / 사람 2명 |

## 결과 문서 틀

### 0. 저장소와 모듈

| 모듈 | 저장소 | 언어·런타임 | 역할 |
|---|---|---|---|

### 1. 아키텍처 레이어
레이어 이름 / 검사 도구·설정 위치 / `domain` 금지 패키지 / 예외

### 2. 코드 컨벤션과 린트
포매터 / 린터·설정 위치·더하거나 뺀 규칙 / 타입 검사 / 커밋 훅 / 에이전트 훅 / 언어 관례 차이 / 기반 오류 이름 / 환경변수 접두어

### 3. API
쓰는 범위와 접두어·호스트 / 범위별 인증 / 폐기 공지 기간 / 속도 제한 / 계약 형식 (도메인 접두어는 도메인 목록)

### 4. DB
DB 종류·위치 / 마이그레이션 도구 / 도메인 구분(스키마·접두어) / 역할 / 백업

### 5. Git
원격·보호 브랜치 / 티켓 키 / gitflow와 다른 점

### 6. CI
진입점 / 일곱 검사의 도구 / CI 서비스·트리거

### 7. 배포
방식과 명령 / 환경 / 정기 주기·시간대 / 멈춤 방법 / 앱 배포 경로

### 8. 테스트
도구 / 통합 테스트 DB / E2E 대상 / 추가 필수 대상

### 9. 의존성
도구·잠금 파일 / 취약점 검사 / 자동 업데이트

### 10~13. AI 협업, 문서 갱신, 장애 사후 분석, 티켓 진행 방식
틀 그대로. 다른 점만.

### 14. 보안
비밀정보 위치 / 인증 방식 / 권한 모델 / 개인정보 / 법·약관 점검표 위치

### 15. 코드 리뷰
리뷰어 / 승인 수 / PR 템플릿 위치

### 줄이는 것 (소규모 프로젝트만)
표준 틀 3절에서 줄이기로 한 것(배포 기록 대기 목록, 기능 문서 등)과 이유
