# <프로젝트> 시스템 설계

시스템 설계는 한 파일에 다 넣지 않고 폴더로 만든다([[30 Areas/Development Standard/프로젝트 표준 틀|프로젝트 표준 틀]] 4.1절).

```text
개발/시스템 설계/
├── 시스템 설계.md        ← 입구: 아래 1~9절 순서, 맨 위에 이 문서 지도
├── 애플리케이션/          ← 4.2 모듈 구성, 7 테스트 전략
│   ├── 흐름/              ← 4.3 주요 흐름(흐름 하나에 문서 하나)
│   └── <모듈>/            ← 저장소를 만들기 전 설계 초안만. 저장소를 만들면 코드 폴더마다 README.md로 옮기고 지운다
├── 데이터/                ← 4.4 데이터
├── 기술·인프라/           ← 4.5 배포·운영(인프라)
├── 보안·규정/             ← 3 제약(법·약관), 5 보안·개인정보
└── 운영/                  ← 5 로깅·모니터링·오류 처리, SLO 설계
```

내용이 없는 폴더는 만들지 않고, 입구의 해당 절에 "미정"과 정할 시점만 적는다.

## 입구 문서 `시스템 설계.md`

1. 맥락과 범위: 기획서·제품 디자인 링크, 사용자, 연결되는 외부 시스템 (입구에 직접)
2. 목표와 비목표 (입구에 직접)
3. 제약: 법·약관·비용·인력 (요점만 입구에, 법·약관 상세는 `보안·규정/`)
4. 설계
   1. 시스템 컨텍스트 그림(C4 1단계) (입구에 직접)
   2. 모듈 구성(C4 2단계): 모듈마다 저장소, 역할, 제공하는 약속 → `애플리케이션/`. 모듈 안의 구조는 저장소(루트 README, 코드 폴더마다 README, API는 docs/interfaces/)
   3. 주요 흐름 → `애플리케이션/흐름/`
   4. 데이터: 저장하는 것, 저장하지 않는 것, 보관 기간 → `데이터/`
   5. 배포·운영(인프라) → `기술·인프라/`. 방식은 프로젝트마다 정하고, 아래 질문에는 모두 답한다(정하지 않은 것은 "미정"과 이유)
      - 어디서 도나: 서버·클라우드, 환경(개발·검증·운영)과 환경 표
      - 어떻게 뜨나: 실행 방식(프로세스 관리·컨테이너), 자동 시작, 배포 방법
      - 누가 어떻게 들어가나: 외부 공개 범위, 접속 방법, 비밀정보 위치
      - 데이터는 안전한가: 백업 주기·보관 위치, 복원을 해 본 날짜
      - 고장 나면 어떻게 아나: 헬스체크, 알림, 로그 위치
      - 얼마 드나: 월 비용, 한도
5. 교차 관심사: 보안·규정, 로깅·모니터링, 오류 처리, 개인정보 → `보안·규정/`, `운영/`
6. 검토한 대안과 버린 이유 (입구에 직접)
7. 테스트 전략 → `애플리케이션/`
8. 단계와 범위(MVP), 위험과 미결 사항 (입구에 직접)
9. 관련 결정 기록 목록 (입구에 직접)

## 나눈 문서

frontmatter에 `standard_version`(틀 버전)과 `related`(입구 문서 링크)를 적는다.
